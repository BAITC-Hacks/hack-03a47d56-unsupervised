# Данные и фильтрация — часть участника №1

Модуль читает исходный CSV, проверяет запрос и оставляет только подходящих подрядчиков. Результат содержит все причины исключения, факты для объяснений и предупреждения о происхождении данных. Работает офлайн на Python 3.10+ без сторонних библиотек и API-ключей.

## Запуск

Из корня ветки `gulya`:

```bash
python -m unittest -v test_filtering
python demo_filtering.py --city Алматы --date 2026-10-01 --event-type свадьба --category Ведущий --budget 1000000
```

Дополнительно: `--language русский --duration-hours 6`. Свой CSV: `--csv "путь к файлу.csv"`. По умолчанию используется `contractors.csv` рядом с модулем, независимо от текущей рабочей папки. `pip install` не требуется. На Windows вместо `python` можно использовать `py -3`.

CLI выводит JSON. Валидный запрос, включая пустую выдачу, завершается с кодом 0; ошибка ввода или CSV — с кодом 2 и JSON в stderr. Не выводите пользователю traceback: ловите `RequestValidationError`, `DataValidationError`, `OSError`.

```python
})

else:

```

`candidates` — обычный `list[dict]` с исходными названиями полей. `categories`, `event_formats`, `languages`, `busy_dates` стали списками; даты — ISO-строки; `price_from_kzt` и `max_hours` — числа, пустой `max_hours` — `None`; флаги — `bool`. `description` сохранён дословно. Весь результат сериализуется в JSON. Входные данные не меняются.

| Поле результата | Назначение |
| --- | --- |
| `status` | `matched`, `no_category_in_city` или `no_matches` |
| `message` | Готовое объяснение исхода, в том числе почему меньше трёх |
| `request` | Проверенный запрос с приведёнными типами |
| `candidates` | Все прошедшие строгие условия, отсортированные по `id` |
| `excluded` | Исключённые из пула города/категории: `id`, `anon_name`, `reasons` |
| `reason_counts` | Счётчики причин, один профиль может учитываться несколько раз |
| `counts` | `catalog`, `city_category`, `eligible`, `excluded` |
| `evidence[id]` | Факты совпадения с полем-источником для будущих объяснений |
| `warnings[id]` | Цена «от», синтетический профиль, заполненные город/цена |
| `calendar_window` | Известное окно календаря включительно |

Причина исключения содержит `code`, `field`, `actual`, `expected`, `message`. Коды: `busy_date`, `over_budget`, `unsupported_format`, `unsupported_language`, `duration_exceeded`.

## Правила

1. Город и категория проверяются первыми: нет такого сочетания в каталоге — `no_category_in_city`. Подстроки не считаются совпадением. У профиля может быть несколько категорий через `|`.
2. Все остальные заданные условия строгие: свободная дата, цена «от» не выше бюджета, поддерживаемый формат, указанный язык, достаточный лимит часов. Равенство бюджету и длительности допустимо. Условия автоматически не ослабляются.
3. `max_hours = None` по заданию означает работу без привязки к присутствию, а не ноль часов. Такой профиль не исключается по длительности.
4. Занятость проверяется одинаково для ведущих, фотографов и площадок. Пустой список занятых дат допустим в пределах известного окна.
5. Календарь покрывает 2026-09-23 — 2026-12-31. Дата вне окна вызывает ошибку ввода: нельзя объявить подрядчика свободным без данных. Прошедшая относительно системных часов дата не отсекается: фиксированные демо должны воспроизводиться.
6. Регистр, Unicode и лишние пробелы нормализуются при сравнении. Синонимы, перевод, исправление опечаток и догадки по описанию не применяются.
7. Отрицательные/бесконечные числа, NaN, bool вместо чисел, нулевая длительность и несуществующая дата отклоняются. Бюджет 0 допустим, включая возможные бесплатные профили. Защитный верхний предел числовых полей — 10^12.
8. Некорректная строка CSV останавливает загрузку с номером строки. Дубликаты ID, пропущенные колонки, неверные флаги и даты не замалчиваются. Заголовок без записей — валидный пустой каталог; файл без заголовка — ошибка.

## Честные объяснения и детерминизм

Этот модуль не вычисляет score и не генерирует финальные карточки: это зона участника №2. Он передаёт факты, которые можно проверить по CSV. В объяснениях следует писать «цена от …», а не обещать окончательную стоимость; доступность означает отсутствие даты в календаре датасета, а не подтверждённое бронирование. UI должен показывать `warnings[id]`, в том числе синтетическое происхождение.

Упорядочивание по `id` стабильно при перестановке входных строк. Нет случайности, сетевых вызовов, зависимости от текущей даты, порядка set или Python hash seed. Ранжирование команды должно сохранить детерминизм своим правилом разрешения равного score.

Не ограничивайте список до трёх до ранжирования. Сначала передайте `result["candidates"]` в ranking, затем выберите до трёх. Пустые исходы и `message` показывайте явно. При успешном результате с менее чем тремя кандидатами также показывайте `message`.

«Я отвечаю за данные и строгую фильтрацию. CSV превращается в проверенные записи: списки, числа, даты и флаги. Сначала выбираем город и категорию, потом проверяем занятость, бюджет, формат и необязательные условия. Каждый отказ объясняется конкретным полем, все причины сохраняются. Мы различаем отсутствие категории и отсутствие подходящих кандидатов. После этого передаём весь допустимый пул ранжированию, а не случайные первые три записи».

## Проверки и интеграция

`python -m unittest -v test_filtering` проверяет реальные 66 профилей, каждый фильтр отдельно, одновременные причины, пустые исходы, площадки, границы дат и чисел, отсутствие мутаций, повреждённый CSV и одинаковый CLI JSON в трёх отдельных процессах с разными `PYTHONHASHSEED`.

Модуль не использует секреты. `.gitignore` исключает `.env`, `.streamlit/secrets.toml`, ключевые файлы и виртуальные окружения. Это не заменяет проверку секретов в будущих коммитах всей команды.

Финальные персональные объяснения, top-3, Streamlit, deployment и объединение веток проверяются участниками №2 и №3 после подключения. Эта ветка реализует часть №1, а не весь готовый продукт.
